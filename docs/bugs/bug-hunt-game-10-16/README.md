## 2. 铁律(违反即判违规)

1. **只读源码。** 禁止对 `packages/`、`scripts/`、`package.json`、`tsconfig*.json` 等任何仓库既有文件做 Edit/Write/删除。
2. **禁止改动 git 状态。** 不得 `commit` / `add` / `stash` / `reset` / `checkout` / `restore` / `clean` / `push` / `rebase`,不得改 `git config`,不得建分支或 worktree。
3. **唯一允许写入仓库的位置**是你自己的两份文档:
   - `bug-hunt-<你的名字>.md`
   - `hunt-review-<你的名字>.md`
   你的名字只能取这四个之一:`claude-code` · `opencc` · `workbuddy` · `trae-code`。
4. **临时文件只进 `/tmp`。** 复现脚本、探针、快照一律写 `/tmp/bughunt-<你的名字>/`(自己 `mkdir -p`)。**禁止**把临时脚本写进仓库任何目录再删(上一届的判例:自曝从轻 −3,隐瞒出局)。
5. **禁止删除或篡改他人文档。**
6. **环节一期间禁止阅读其他选手的 `bug-hunt-*.md`。** 你的判断必须独立形成。这是本赛制最容易被自我污染的一条——先看了别人的报告,你后面写的每一条都可能被污染,评审也无法区分原创与跟风。
7. **禁止全量测试。** `pnpm -r test` 会跑 520+ 文件 / 约 4.5 分钟,AGENTS.md 明令禁止。只跑单文件或指定文件,且**必须重定向到日志文件再读**(见 §3.1)。另外 `packages/zai/vitest.config.ts` 的 `fileParallelism: false` 是**有意保留的兜底**(撤回它会稳定复现 PdfRenderer 翻页与 replHistory 30s 超时两类 flaky),**任何「跑全量看到红」的论证一律无效**(见 §3.2 第 4 条)。
8. **禁止动用户真实数据与端口。** 详见下面两条,这是本仓库最硬的约束。
9. **禁止用 tmux / 浏览器自动化驱动用户正在跑的 zai 实例。** 用户线上实例在跑,那是共享状态。
10. **隔离 `ZAI_DATA_DIR` 铁律(本仓库专有)。** `packages/zai/src/server/services/paths.ts:23` 读 `process.env.ZAI_DATA_DIR || join(homedir(), '.zai')`。**任何会触碰数据目录的复现脚本,必须显式设 `ZAI_DATA_DIR=/tmp/bughunt-<你>/zai-home`**,并在脚本头部注明。`~/.zai/` 里有用户的真实会话、插件缓存、微信 pairing 凭据与 context token——写坏它不是「污染工作区」,是毁用户数据。**不隔离就动 `~/.zai/` 的,按 §8 顶格处理。**
11. **端口铁律:** 默认端口是 **9201**,那是用户正式实例。**禁止 kill 920x 上的任何进程**,禁止用默认端口起你自己的实例。需要起服务时用空闲端口(如 `--port 8101 --api-port 7715`),并先 `lsof -i :<port>` 确认(见 §3.2 第 2 条)。
12. **禁止编造。** 没有验证过的行为不许写成「已复现」。不确定就降证据等级(§4.2)写「未验证」,这不丢人,编造才丢人。

违规扣分见 §8。

## 3. 取证环境

### 3.1 可以用(节选)

```bash
# 基线快照(§3.3)
git rev-parse HEAD > /tmp/bughunt-<你>/head.txt
git status --porcelain > /tmp/bughunt-<你>/status-before.txt

# 类型检查:两个包都是 exit 0(§3.4)
pnpm --filter @zn-ai/zai run typecheck         > /tmp/bughunt-<你>/tc-zai.log  2>&1; echo "exit=$?"
pnpm --filter @zn-ai/zn-agent-core run typecheck > /tmp/bughunt-<你>/tc-core.log 2>&1; echo "exit=$?"

# 单文件 / 指定文件测试。必须重定向,禁止 | tail
pnpm --filter @zn-ai/zai test src/server/routes/fs.test.ts > /tmp/bughunt-<你>/t.log 2>&1
grep -cE '^\s*(×|✗|FAIL)' /tmp/bughunt-<你>/t.log     # 统计失败数
pnpm --filter @zn-ai/zn-agent-core test <path> > /tmp/bughunt-<你>/t2.log 2>&1  # 跨包不要混跑

# 起一个隔离实例(必须换端口 + 必须隔离数据目录)
ZAI_DATA_DIR=/tmp/bughunt-<你>/zai-home \
  pnpm --filter @zn-ai/zai dev -- --port 8101 --api-port 7715 > /tmp/bughunt-<你>/dev.log 2>&1 &

# 检索:用 Grep / Glob 工具,不要在 Bash 里手搓 rg/grep
# 理解代码优先 codegraph_explore(单调用,索引未初始化跑 codegraph init -i)
```

> 起 dev 时 `--` 是必需的,`--port` / `--api-port` 是 zai CLI 的参数,要靠 pnpm 的 `--` 透传。**禁止顶层 `pnpm dev`**(会同时拉起 core 的 `tsc -b --watch`,它拒绝 `--port`,整链失败)。

### 3.2 七个已知坑(所有选手都会踩,先记住)

1. **PATH 上的 `opencc` 与本仓库无关。** 本仓库的产品是 `zai`(`/Users/ethan/code/opencc-web`),不是 `opencc`(`/Users/ethan/code/opencc`)。你要验证的是**本仓库**的行为,入口是 `pnpm --filter @zn-ai/zai dev`,产物是 `packages/zai/dist/`。

2. **9201 是用户的正式实例。** 直接 `pnpm dev` 或不带 `--port` 起服务会撞上它;更糟的是 `packages/zai/src/cli/ports.ts:112-113` 记录的 split-brain:macOS/BSD 上通配 bind(`*:9201`,即 `--lan` 模式)**不阻止**后续的具体 bind(`127.0.0.1:9201`),于是两个实例共享同一份 API key 打请求风暴。**永远显式指定一个确认空闲的端口。**

3. **`dist/` 与 `src/` 不同步。** `packages/*/dist/` 全是构建产物,不是源码。改了 `zn-agent-core`(含 vendor)必须 `pnpm run build:core` 才生效。**读了 `dist/` 得出「代码没问题」的结论,可能只是产物过期**——反过来,拿 `dist/` 里一段看似残留的死代码报 bug,可能那行在 `src/` 里早删了。**读源码,不要读产物;但要意识到自己起的服务跑的是产物。**

4. **本仓库有预存 flaky,无改动跑出来的红一律不算你发现的 bug。** 至少两类已知:全量并发下的 PdfRenderer 翻页用例、replHistory `?q=` 前缀过滤 30s 超时。两者隔离单跑 100% 稳定。判断「这是我发现的」必须给出因果:从哪一行代码、因为什么逻辑,导致这个失败。任何依赖「看起来是红的」的论证都不成立(上一届铁律,原样保留)。

5. **vendor 里约 230 个 `.tsx` 组件体已被就地 stub 成 `return null`**(2026-10-04 的处理,共 586 个 `.tsx`),另有 8 个文件带 `// Stub — …not included in source snapshot` 标记。**读这些文件找不到 UI 逻辑,不要把 stub 报成 bug**——「这个组件什么都不渲染」不是缺陷,是被有意移除的终端 UI。这是本仓库特有的假阳性制造机,详见 `DEVELOPMENT_REFERENCE.md` §19。

6. **大量模块级单例。** 上一届 wb-r01 的对照组就是被模块级 LRU 吃掉的。本仓库同样满地都是:三个单例 registry、instanceStore、session registry、weixin account locks、端口解析器。**任何探针如果跨对照复用了模块级状态,你的对照组就是假的**(见 §4.7)。裁决时我会重点看你有没有显式复位。

7. **前端行为不要用单测判红绿。** 样式改动、`happy-dom` 下的 DOM 结构断言,红绿没有意义(AGENTS.md 明确要求样式改动用 `/ego-browser` 度量)。同理,React 组件树的真实行为属于 §4.2 的 E3b 范畴,不是「跑个 render 就完事」。

`docs/bugs/bug-hunt-game-10-16/bug-hunt-<你的名字>.md`,结构见 [`TEMPLATE-bug-hunt.md`](./TEMPLATE-bug-hunt.md)。至少包含:

### 4.2 证据等级(决定这条 bug 值多少分)

| 等级 | 含义 | 判定标准(裁判据此打分) |
|---|---|---|
| **E3b** | **组件层 / 前端 / 端到端行为**的机器可证 | 真实执行了被测模块**在其真实调用方之中**的行为,并断言可观测结果(渲染出的 DOM/文本、真实 HTTP 响应体、事件序列)。对 React 缺陷 = **实际把组件树渲染出来**(vitest + happy-dom,或起真服务用浏览器/curl);对 HTTP 缺陷 = **起隔离实例打真实端点** |
| **E3a** | **模块自身**行为的机器可证 | 附一个能跑的最小复现物,放 `/tmp/bughunt-<你>/`,文档里给出**完整命令与真实输出**。测试必须真实执行被测模块,禁止用 `vi.mock` / `mock.module` 把**被测对象本身**替换掉 |
| **E2** | 可复现 | 给出确定的触发输入/操作步骤 + 观察到的错误行为 |
| **E1** | 静态可证 | 无需运行即可判定:精确 `file:line` + 从入口到出错点的完整调用链 + 为什么现有防护挡不住 + 错误后果推演 |
| **E0** | 仅推测 | 读代码感觉不对。**不计分**。不是惩罚,是这类条目本来就不构成发现 |

**组件层缺陷若只达到 E3a,按 E2 计分。**

> **为什么拆成 a / b。** 上一届的规则只要求「真实执行被测模块」,拦不住一类特殊的假证据:脚本调 `transformModRenderText(H(text))`,观察到输出被套两遍,于是宣称「渲染链被套两遍」。脚本确实跑了真实模块,满足字面要求——但它证明的是「*函数被调用两次*会套两遍」(恒真式),命题却是「*React 树会对同一段文本调用两次*」。**上一届裁判把这条判成全场最高分,修复阶段自己推翻了。** 本仓库前端 80 个组件 + 大量 SSE/流式行为,正是这条坑的高发区。

**每个 E3 必须标注执行运行时**(本场新增硬性字段):

```markdown
- **执行环境**：运行时 Node v22.22.3(产品运行时) · 测试工具链 vitest 5.0.3 · 平台 darwin-arm64
- **为什么这个环境代表用户**：<一句话。产品是 Node-direct(dev 用 tsx + bun-protocol loader);若你用 dev:bun 跑的,必须说明为什么它也能代表用户>
```

> 上一届 oc-002 的修复在 Node 生效、在 Bun 失效(Bun 忽略 file: URL 上的 `?query`),而当时的测试工具链是 Bun——**任何回归测试都给假绿**。若某条 E3 的结论只在非产品运行时下成立,裁判按 E2 计。

> 探测过程中产生大量 E0 是正常的。写进「自我否定清单」即可,不要塞进正式报告占位。

**「当前不可触发」的自证义务。** 若你声称某缺陷机制成立但当前不可达(如「全仓无创建点」「生产入口每次都 new」),必须附**不可触发的依据**:全仓搜索的范围与命令、构造点的枚举、或一个能覆盖未来创建的守卫测试。**无法自证的,按 E1 计**(机制成立但触发性未证)。裁判复核「不可触发」时会独立重跑该搜索,不接受你的转述。

### 4.3 严重度(决定基数)

| 级别 | 判据 | 基数分 |
|---|---|---|
| **S1 阻断级** | 崩溃 / 数据损坏 / 越权 / 凭证泄露 / 静默丢用户工作 / 会话串号 | 10 |
| **S2 核心功能错误** | API 返回错误结果、请求发错目标、跨会话状态污染、SSE 断点后的事件丢失、权限判定错误 | 6 |
| **S3 边界退化** | 边界条件算错、错误路径不清理/不释放、提示缺失、轻微泄漏、UI 局部错位 | 3 |
| **S4 健壮性隐患** | 有风险但当前不可触发或影响极小 | 1 |

> 本仓库的高危面集中在:`/api/exec` 一类简单请求端点、`fs` 路由的路径解析、微信通道的游标/锁、SSE 的 seq 与订阅表、PTY 的回收、`~/.zai/` 的写入原子性。**上一届 opencc 的 22 条已知缺陷已经把这几条主路径扫过一遍(见 §3.4),你的价值在它们没扫到的地方。**

**虚报惩罚**:把低严重度报成高严重度,环节二未被证伪、但裁判复核为低严重度的,按**低严重度**计分,且该选手发掘分 **-3**/条。(判例:上一届对「跌一档」罚 −3、「跌两档」只降档不罚,本场沿用。)

### 4.4 单条 bug 的必填格式

- **触发路径**：用户动作 → `entry()` (packages/zai/src/a.ts:10) → `handler()` (packages/zai/src/b.ts:88) → 出错点
- **现象**：预期 ……;实际 ……

- **对照组**(E3 必填):<对照组是什么、它的输出、以及它为什么有区分力——见 §4.7>

### 4.6 环节一质量红线

- 不得凑数:同一根因的多个表现算**一条**,不要拆成五条刷数量。
- 不得把「代码风格」「命名不好」「没有注释」当 bug。
- 不得把上游设计如此的行为当 bug(若你认为有改进空间,请放到「自我否定清单」并标注为改进建议)。
- 不得把 vendor stub(§3.2 第 5 条)当 bug。
- **质量优先于数量**:10 条 E3b 的价值远高于 50 条 E1。

### 4.7 对照组硬性要求(本场新增)

**每条 E3 复现物必须含对照组,且对照组要证明「如果没有这个 bug,输出会不同」。**

具体要求:

1. **对照组先跑一遍,贴输出。** 如果对照组的输出与实验组相同,它没有区分力,等于没做。
2. **探针用到模块级缓存 / 单例 / 全局状态时,每次对照前必须显式复位**,并在脚本里说明复位的调用。本仓库的模块级单例密度极高(§3.2 第 6 条),这一条不是形式主义。
3. 裁判的复核脚本**同样适用**本条——裁判会在自己的复核记录里贴对照组输出。

> 上一届这条规则缺失的代价:选手的对照组被模块级 LRU 吃掉却没人发现,裁判判「结论正确只是执行失效」,**而结论本身也不成立**。两层错误叠在一起,让一条假发现拿了全场最高分。上一届裁判在勘误里写下了这个反面教材,本场规则补上。

## 5. 环节二 · 交叉评审

环节一收口后开放。你要读**另外三位**选手的 `bug-hunt-*.md`,逐一裁决。

### 5.1 交付物

`docs/bugs/bug-hunt-game-10-16/hunt-review-<你的名字>.md`,结构见 [`TEMPLATE-hunt-review.md`](./TEMPLATE-hunt-review.md)。

### 5.2 裁决枚举(对他人每一条都判)

| 裁决 | 含义 | 你的理由必须包含 |
|---|---|---|
| `CONFIRMED` | 问题真实存在 | 你在源码里核到的 `file:line` + 成立的理由 |
| `PARTIAL` | 问题真实存在但作者说错了严重度/触发条件/影响范围 | 错在哪,作者的版本应该怎么改写 |
| `REJECTED` | 问题不存在或不构成缺陷 | **具体指出作者推理的哪一步断了**,不能只说「我看不出来」 |
| `NOT-ENOUGH-EVIDENCE` | 可能真,但作者给的证据不足以支撑其严重度/触发条件 | 还缺什么证据才能成立 |
| `DUPLICATE` | 与另一位选手报告的是同一处 | 标注 `DUPLICATE-OF: <对方 ID>`;**双方都照常计分** |
| `KNOWN` | 该条已在 `docs/bugs/` 的 22 条已知未修清单里 | 标注 `KNOWN-OF: docs/bugs/<文件名>`。**该条目双方均 0 分**(§3.4) |

> **关键:你的裁决必须落在源码上,不能只落在对方文档上。** 评审时至少要 `Read` 到每一处被引用的 `file:line`,确认行号所指的东西和作者描述一致。这一条裁判会抽查(见 §6.2「行号核实」)。

### 5.3 抽验要求(硬性)

对你判为 `CONFIRMED`/`REJECTED` 的条目,**至少抽 3 条**(跨不同选手、不同严重度)**亲手复验**:

- 复验方式不限(读源码追调用链 / 跑单文件 vitest / 跑 `/tmp` 下的最小复现物 / 起隔离实例打真实端点)。
- 在报告里单列 `## 抽验记录` 一节,逐条写:我做了什么、看到了什么、结论是否与作者一致。

没做抽验直接照抄作者结论的,评审分大幅扣减。

### 5.4 主动新发现(硬性)

单列 `## 评审中额外发现` 一节,分两类:

1. **`## 评审中额外发现`(新缺陷)** — 评审过程中你在源码里抓到、但不在任何一份原报告里的**问题**。**至少 1 条**(真有就多写,没有就写「未发现额外问题」并列出你实际看过的地方)。
2. **`## 交叉洞察`(非新缺陷,也计分)** — 你对**已在某份报告里的缺陷**补上了作者没做的验证,或论证了某条裁决错了。**至少 1 条**。

> 第 2 类是本场修订(§0.1 第 9 条)。上一届规则里「主动新发现」按字面只算新缺陷,结果本场质量最高的两条评审输出——claude-code 把 cc-010 与 oc-012 叠起来指出「单独修任一条仍会静默丢活」、论证 trae-code 否决「按 mod 粒度失效」的理由有误——**都是 0 分**,而它们的质量高于任何一条被计分的新发现。本场把这类输出正式纳入计分,但**上限压低**,避免变成刷分项。

**这两节都不是可选礼貌。** 它们是对抗「读文档不读代码」最直接的检验手段:只会复读别人报告的人,这两节必然是空的。

### 5.5 评审质量红线

- 不得因为「我觉得不可能」就 `REJECTED`——必须指出推理断点。
- 不得把 `PARTIAL` 当 `REJECTED` 用来逃避思考。
- **不得把「docs/bugs/ 里已知」当成不读源码的理由**——判 `KNOWN` 也要核过行号。
- 误杀真 bug(裁判终裁为 `CONFIRMED` 而你判 `REJECTED`)是评审环节**最严重的错误**,单独扣分(§6.2)。

### 6.1 裁判自查(裁判自己的纪律,先声明)

### 6.2 计分公式(满分 100)

**发掘分 60**

```
单条得分 = 严重度基数(S) × 证据系数(E)
严重度基数:S1=10, S2=6, S3=3, S4=1
证据系数:  E3b=1.0, E3a=1.0, E2=0.8, E1=0.5, E0=0
同一条缺陷被多人发现:各人照常计分(不设唯一归属)
在 docs/bugs/ 已知清单里的:0 分(双方都是)
发掘分 = Σ(有效条目得分),上限 60
```

量级参考(算式已展开,据此自测你的产出处在什么水位):

| 典型产出 | 算式 | 发掘分 |
|---|---|---|
| 3 条 S2/E2 | 6×0.8 ×3 | 14.4 |
| 5 条 S2/E3 | 6×1.0 ×5 | 30 |
| 1×S1/E3 + 5×S2/E3 + 2×S3/E2 | 10 + 30 + 4.8 | 44.8 |
| 2×S1/E3 + 6×S2/E3 | 20 + 36 = 56 | 56 |
| 3×S1/E3 + 7×S2/E3 | 30 + 42 = 72 | 打满 60 |

额外扣分:
- 提交中 `E0` 占比 > 50%(正式报告区,不含自我否定清单)→ 记「低证据密度」,**评审分 -5**。
- 严重度虚报(§4.3)→ **-3/条**。
- 违规(§8)→ 见扣分表。

**评审分 40**

| 项 | 分值 | 规则 |
|---|---|---|
| 裁决正确率 | 20 | 每条 2 分;与裁判终裁不一致 **-2**;**误杀真 bug(真 CONFIRMED 被你判 REJECTED)额外 -1**;**放过真缺陷(裁判终裁 CONFIRMED 而你判 NOT-ENOUGH-EVIDENCE)额外 -1** |
| 抽验质量 | 12 | 抽验条目中「你的复验结论与事实一致」的比例 × 12;未做抽验直接给 0 |
| 主动新发现 | 8 | 按 `S×0.5` 计:S1=5, S2=3, S3=1.5, S4=0.5(以裁判复核为准) |
| 交叉洞察 | 4 | §5.4 第 2 类,按 `S×0.3` 计:S1=3, S2=1.8, S3=0.9, S4=0.3。**上限 4** |
| 行号核实 | 扣分项 | 裁判抽查 3 条你的引用,核错一处 **-2** |

**真正值钱的 bug 在缝隙里**:

- **跨模块契约不一致** — `packages/zai`(Express+SSE)与 `packages/zn-agent-core`(vendor opencc + compat 垫片)之间的假设。`src/compat/` 这层垫片的每个函数都是一个「两套实现语义不一致」的机会。
- **模块级单例的生命周期** — 本仓库注册表密度极高。三个单例 registry、instanceStore、session registry、weixin account locks、PTY 会话表。上一届 opencc 的核心发现是「10 个缺陷收敛到同一个设计缺陷:状态分散在多个注册表,移除路径只清了其中几个」。**本仓库大概率有同构问题。**
- **异步竞态与状态残留** — Express 4 不转发 async rejection、SSE 订阅注册晚于 `await`、`req.on('close')` 的语义(`docs/bugs/` 里有两条相关已知缺陷,但同类形状未必只有那两处)。
- **fork 特有改造** — `src/compat/sandboxManager.ts`、`src/compat/permissions.ts`、`src/compat/dangling-shims/`(名字就在提示你)、`src/compat/subprocess/`。
- **vendor 同步依赖人工判断** — `AGENTS.md` 记录过一次「以上游不存在该不对称为由跳过了上游的安全补丁」,结论对、推理错。`docs/mods-vendor-divergences.md` 是这类判断的账本。
- **特性开关与部署形态** — `--lan` 模式打破「只监听 localhost」这个安全前提、微信通道只跑在受管子实例、`ZAI_DATA_DIR` 的静态 import vs 函数重读(`paths.ts` 注释里已经点出这个不对称)。

**不要为了赢而堆 E0。** 一条被裁判亲自核实为真的 S2,比二十条看起来很专业的猜测值钱得多——而猜错还要倒扣。

**也不要为了显得严谨而堆 E1。** 本场的 typecheck 基线是干净的(exit 0),所以 typecheck 红的信号很强;但**它抓不到运行时行为问题**,而后者才是这个仓库的主要缺陷面。E1 是起点,不是终点。
