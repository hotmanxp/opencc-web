## 2. 铁律(违反即判违规)

1. **只读源码。** 禁止对 `packages/`、`scripts/`、`package.json`、`tsconfig*.json` 等任何仓库既有文件做 Edit/Write/删除。
2. **禁止改动 git 状态。** 不得 `commit` / `add` / `stash` / `reset` / `checkout` / `restore` / `clean` / `push` / `rebase`,不得改 `git config`,不得建分支或 worktree。
3. **唯一允许写入仓库的位置**是你自己的两份文档:
   - `bug-hunt-<你的名字>.md`
   - `hunt-review-<你的名字>.md`
   你的名字只能取这两个之一:`opencc` · `claude`。
4. **临时文件只进 `/tmp`。** 复现脚本、探针、快照一律写 `/tmp/bughunt-<你的名字>/`(自己 `mkdir -p`)。**禁止**把临时脚本写进仓库任何目录再删(上届判例:自曝从轻 −3,隐瞒出局)。
5. **禁止删除或篡改他人文档。**
6. **环节一期间禁止阅读对方(以及上一届任何选手)的 bug 报告。** 你的判断必须独立形成。上一届的铁律,原样保留。
7. **禁止全量测试。** `pnpm -r test` 会跑 520+ 文件 / 约 4.5 分钟,AGENTS.md 明令禁止。只跑单文件或指定文件,且**必须重定向到日志文件再读**(见 §3.1)。`packages/zai/vitest.config.ts` 的 `fileParallelism: false` 是**有意保留的兜底**,**任何「跑全量看到红」的论证一律无效**(见 §3.2 第 4 条)。
8. **禁止动用户真实数据与端口。** 详见下面两条,这是本仓库最硬的约束。
9. **禁止用 tmux / 浏览器自动化驱动用户正在跑的 zai 实例。**
10. **隔离 `ZAI_DATA_DIR` 铁律。** `packages/zai/src/server/services/paths.ts:23` 读 `process.env.ZAI_DATA_DIR || join(homedir(), '.zai')`。**任何会触碰数据目录的复现脚本,必须显式设 `ZAI_DATA_DIR=/tmp/bughunt-<你>/zai-home`**,并在脚本头部注明。`~/.zai/` 里有用户的真实会话、插件缓存、微信 pairing 凭据与 context token——写坏它不是「污染工作区」,是毁用户数据。**不隔离就动 `~/.zai/` 的,按 §8 顶格处理。**
    > **上一届的实测警告**:设了 `ZAI_DATA_DIR` **仍然**读写用户真实 `~/.zai/settings.json`(`oc-001`),compat 侧还有另一条不同写法的漏网路径(`tc-002`,`${process.env.HOME ?? '/tmp'}/.zai`,模板串绕开了 `join(homedir()` 这个 grep 特征)。**收口要跨 `packages/zai` 与 `packages/zn-agent-core` 两个象限,只查一个包的 grep 一定不完整。** 且上届 `cc-r2` 补上的一块更重:boot 期 permissions backfill 是**无条件自动写**,隔离实例一启动就改写用户真实配置。

12. **禁止编造。** 没有验证过的行为不许写成「已复现」。不确定就降证据等级(§4.2)写「未验证」,这不丢人,编造才丢人。

### 3.2 七个已知坑(所有选手都会踩,先记住)

1. **PATH 上的 `opencc` 与本仓库无关。** 本仓库的产品是 `zai`。你要验证的是**本仓库**的行为,入口是 `pnpm --filter @zn-ai/zai dev`,产物是 `packages/zai/dist/`。
2. **9201 是用户的正式实例。** 直接 `pnpm dev` 或不带 `--port` 起服务会撞上它;更糟的是 `packages/zai/src/cli/ports.ts:112-113` 记录的 split-brain:macOS/BSD 上通配 bind(`*:9201`,即 `--lan` 模式)**不阻止**后续的具体 bind(`127.0.0.1:9201`),于是两个实例共享同一份 API key 打请求风暴。**永远显式指定一个确认空闲的端口。**
3. **`dist/` 与 `src/` 不同步。** 改了 `zn-agent-core`(含 vendor)必须 `pnpm run build:core` 才生效。**读了 `dist/` 得出「代码没问题」的结论,可能只是产物过期**;反过来,拿 `dist/` 里一段看似残留的死代码报 bug,可能那行在 `src/` 里早删了。**读源码,不要读产物;但要意识到自己起的服务跑的是产物。**
4. **本仓库有预存 flaky,无改动跑出来的红一律不算你发现的 bug。** 至少两类已知:全量并发下的 PdfRenderer 翻页用例、replHistory `?q=` 前缀过滤 30s 超时。两者隔离单跑 100% 稳定。判断「这是我发现的」必须给出因果:从哪一行代码、因为什么逻辑,导致这个失败。
5. **vendor 里约 230 个 `.tsx` 组件体已被就地 stub 成 `return null`**(共 586 个 `.tsx`),另有 8 个文件带 `// Stub — …not included in source snapshot` 标记。**读这些文件找不到 UI 逻辑,不要把 stub 报成 bug**——「这个组件什么都不渲染」不是缺陷,是被有意移除的终端 UI(详见 `DEVELOPMENT_REFERENCE.md` §19)。
6. **大量模块级单例。** 三个单例 registry、instanceStore、session registry、weixin account locks、PTY 会话表、端口解析器。**任何探针如果跨对照复用了模块级状态,你的对照组就是假的**(见 §4.7)。
7. **前端行为不要用单测判红绿。** 样式改动、`happy-dom` 下的 DOM 结构断言,红绿没有意义(AGENTS.md 明确要求样式改动用 `/ego-browser` 度量)。React 组件树的真实行为属于 §4.2 的 E3b 范畴。

### 4.2 证据等级(决定这条 bug 值多少分)

| 等级 | 含义 | 判定标准 |
|---|---|---|
| **E3b** | **组件层 / 前端 / 端到端行为**的机器可证 | 真实执行了被测模块**在其真实调用方之中**的行为,并断言可观测结果(渲染出的 DOM/文本、真实 HTTP 响应体、事件序列)。对 React 缺陷 = **实际把组件树渲染出来**;对 HTTP 缺陷 = **起隔离实例打真实端点** |
| **E3a** | **模块自身**行为的机器可证 | 附一个能跑的最小复现物,放 `/tmp/bughunt-<你>/`,文档里给出**完整命令与真实输出**。测试必须真实执行被测模块,禁止用 `vi.mock` / `mock.module` 把**被测对象本身**替换掉 |
| **E2** | 可复现 | 给出确定的触发输入/操作步骤 + 观察到的错误行为 |
| **E1** | 静态可证 | 无需运行即可判定:精确 `file:line` + 从入口到出错点的完整调用链 + 为什么现有防护挡不住 + 错误后果推演 |
| **E0** | 仅推测 | 读代码感觉不对。**不计分**。不是惩罚,是这类条目本来就不构成发现 |

**组件层缺陷若只达到 E3a,按 E2 计分。**

> **为什么拆成 a / b。** 规则只要求「真实执行被测模块」,拦不住一类假证据:脚本调 `transformModRenderText(H(text))`,观察到输出被套两遍,于是宣称「渲染链被套两遍」——它证明的是「*函数被调用两次*会套两遍」(恒真式),命题却是「*React 树会对同一段文本调用两次*」。**上一届裁判把这样一条判成全场最高分,修复阶段自己推翻了。**

#### 4.2.1 E1 条目强制「前置可达性三问」(本场新增硬性)

**每一条 E1 必须逐条回答三个问题,答不出的按 S4 计(不是不给分,是给最低档)。**

| 问 | 要求 |
|---|---|
| **①谁创建这个状态?** | 枚举出**生产代码**里所有能让该状态出现的构造点 / 赋值点,给 `file:line`。不能只列一个。 |
| **②生产默认配置下可达吗?** | 说明默认部署形态(`pnpm dev` 本机单实例 / `--lan` / 受管子实例 / `--aa` 启动)下,这条路径是否真的会被走到。**若需要某个非默认开关、某个只在测试里设的 env、或某个上游 CLI 才注入的值,必须写明。** |
| **③现有防护为什么挡不住?** | 把每道已存在的守卫逐条列出并说明为何不覆盖这个输入;若「根本没有防护」也要说明你搜过哪些位置。 |

> **为什么加这条。** 上一届冠军 workbuddy 的 12 条有 7 条被降档,**方向高度一致**:定位、行号、调用链精度极高(五处行号零偏移),失真全部集中在最后一跳。最贵的一条 `wb-010`——代码洞是真的(`WebFetchTool/utils.ts:304-306` 的裸 `fetch` 确实绕过 SSRF 守卫),但全仓仅 3 处提及 `OPENCC_WEBTOOL_ENABLE`,**zai 从不设置,该工具默认不在工具池**。前置可达性没查,整条塌成 S4。
>
> 反面也成立:上一届 opencc 的 `oc-001`(设了 `ZAI_DATA_DIR` 仍读写真实 `~/.zai/settings.json`)之所以是全场最高分,正因为它**把隔离后的实例真跑起来、植入了哨兵值**,读与写双向都实测到。**E1 不是原罪,「E1 且没做可达性排查」才是。**

**每个 E3 必须标注执行运行时:**

```markdown
- **执行环境**：运行时 Node v22.22.3(产品运行时) · 测试工具链 vitest 5.0.3 · 平台 darwin-arm64
- **为什么这个环境代表用户**：<一句话。产品是 Node-direct;若你用 dev:bun 跑的,必须说明为什么它也能代表用户>
```

> 上届 oc-002 的修复在 Node 生效、在 Bun 失效(Bun 忽略 file: URL 的 `?query`),任何 `bun test` 回归测试都给假绿。若某条 E3 的结论只在非产品运行时下成立,裁判按 E2 计。

**「当前不可触发」的自证义务。** 若你声称机制成立但当前不可达,必须附**不可触发的依据**:全仓搜索的**范围与命令**、构造点的枚举、或一个能覆盖未来创建的守卫测试。**无法自证的,按 E1 计**。裁判复核时会独立重跑该搜索,不接受转述。

### 4.3 严重度(决定基数)

| 级别 | 判据 | 基数分 |
|---|---|---|
| **S1 阻断级** | 崩溃 / 数据损坏 / 越权 / 凭证泄露 / 静默丢用户工作 / 会话串号 | 10 |
| **S2 核心功能错误** | API 返回错误结果、请求发错目标、跨会话状态污染、SSE 断点后的事件丢失、权限判定错误 | 6 |
| **S3 边界退化** | 边界条件算错、错误路径不清理/不释放、提示缺失、轻微泄漏、UI 局部错位 | 3 |
| **S4 健壮性隐患** | 有风险但当前不可触发或影响极小 | 1 |

**虚报惩罚**:把低严重度报成高严重度,环节二未被证伪、但裁判复核为低严重度的,按**低严重度**计分,且该选手发掘分 **-3**/条(跌一档罚;跌两档只降档不罚)。
> 上届四条降档**都没触发**罚则——因为它们都被三位评审判了 CONFIRMED,即「环节二已被证伪」不成立。这条口径本场沿用。

### 4.6 环节一质量红线

- **不得凑数**:同一根因的多个表现算**一条**。
- **不得把「代码风格」「命名不好」「没有注释」当 bug。**
- **不得把上游设计如此的行为当 bug**(放「自我否定清单」并标注为改进建议)。
- **不得把 vendor stub(§3.2 第 5 条)当 bug。**
- **不得把 §3.4 的已知清单换个说法重报。**
- **质量优先于数量**:上一届发覆盖面赢,但赢在「失真方向一致所以累加仍第一」,不是赢在条数本身。

### 4.7 对照组硬性要求

**每条 E3 复现物必须含对照组,且对照组要证明「如果没有这个 bug,输出会不同」。**

1. **对照组先跑一遍,贴输出。** 如果对照组输出与实验组相同,它没有区分力,等于没做。
2. **探针用到模块级缓存 / 单例 / 全局状态时,每次对照前必须显式复位**,并在脚本里说明复位的调用。
3. **裁判的复核脚本同样适用本条**——裁判会在自己的复核记录里贴对照组输出。

> 上一届这条规则缺失的代价:某选手的对照组被模块级 LRU 吃掉却没人发现,裁判判「结论正确只是执行失效」,**而结论本身也不成立**。两层错误叠在一起,让一条假发现拿了全场最高分。**上一届裁判自己踩了同一个坑**(错误 envelope 让 `set()` 根本没跑,测试照样「通过」)。本场规则不变。

## 5. 环节二 · 交叉评审

环节一收口后开放。你要读**对方**的 `bug-hunt-<对方名字>.md`,**逐一裁决对方的每一条**。

### 5.1 交付物

`docs/bugs/bug-hunt-game-10-17/hunt-review-<你的名字>.md`,结构见 [`TEMPLATE-hunt-review.md`](./TEMPLATE-hunt-review.md)。

### 5.2 裁决枚举(对对方每一条都判)

| 裁决 | 含义 | 你的理由必须包含 |
|---|---|---|
| `CONFIRMED` | 问题真实存在 | 你在源码里核到的 `file:line` + 成立的理由 |
| `PARTIAL` | 问题真实存在但作者说错了严重度/触发条件/影响范围 | 错在哪,作者的版本应该怎么改写 |
| `REJECTED` | 问题不存在或不构成缺陷 | **具体指出作者推理的哪一步断了**,不能只说「我看不出来」 |
| `NOT-ENOUGH-EVIDENCE` | 可能真,但作者给的证据不足以支撑其严重度/触发条件 | 还缺什么证据才能成立 |
| `DUPLICATE` | 与已知清单或上一届条目同源 | 标注 `DUPLICATE-OF: <来源>`;**双方都照常计分**,只有 §3.4 已知清单才是 0 分 |
| `KNOWN` | 该条已在 §3.4 的已知未修清单里 | 标注 `KNOWN-OF: <文件或 ID>`。**该条目双方均 0 分** |

> **关键:你的裁决必须落在源码上,不能只落在对方文档上。** 至少要 `Read` 到每一处被引用的 `file:line`,确认行号所指的东西和作者描述一致。裁判会抽查。

**主动触发对方修正是允许的**:如果对方某条的前三问(§4.2.1)没答,你可以要求补答,这本身是一条有价值的评审产出。

### 5.3 抽验要求(硬性)

对判为 `CONFIRMED` / `REJECTED` 的条目,**至少抽 3 条**(跨不同严重度)**亲手复验**:

- 复验方式不限(读源码追调用链 / 跑单文件 vitest / 跑 `/tmp` 下的最小复现物 / 起隔离实例打真实端点)。
- 单列 `## 抽验记录` 一节,逐条写:我做了什么、看到了什么、结论是否与作者一致。

> **上一届最有价值的一次抽验值得记住**:有选手去证伪最重的那条 S1,跑出来「8 次里 4 次全丢、其余丢 1~3 条」,直接推翻了对方标题里「5/5 条**确定性**丢失」这个**可证伪的失真**——结论仍成立(S2 不受影响),但断言站不住。**抽验的价值常常不在于推翻结论,而在于把「看起来很确定」的数字变成诚实的表述。**

### 5.4 主动新发现 + 交叉洞察(两节都是硬性的)

单列两节:

1. **`## 评审中额外发现`(新缺陷)** — 评审过程中你在源码里抓到、但不在对方报告里的**问题**。**至少 1 条**(没有就写「未发现额外问题」并列出你实际看过的地方)。
2. **`## 交叉洞察`(非新缺陷,也计分)** — 你对**对方报告里已有缺陷**补上了作者没做的验证,或论证了某条裁决错了。**至少 1 条**。**综合复述别人的结论不算**——必须补上新的验证动作或新的推理。

> **两栏互斥(本场新增,修上届的规则漏洞)**:同一个事实**只能在一栏计分**。裁判按更完整的一栏计分,另一栏记 0——**这是规则澄清,不是对选手的处罚**,选手无需为此自责,但要知道两栏不会各给一次分。

### 5.5 评审质量红线

- 不得因为「我觉得不可能」就 `REJECTED`——必须指出推理断点。
- 不得把 `PARTIAL` 当 `REJECTED` 用来逃避思考。
- **不得把「§3.4 里已知」当成不读源码的理由**——判 `KNOWN` 也要核过行号。
- 误杀真 bug(裁判终裁为 `CONFIRMED` 而你判 `REJECTED`)是评审环节**最严重的错误**,单独扣分。

## 6. 环节三 · 裁判与排名

由裁判执行,产出 `VERDICT.md` + `ANNOUNCEMENT.md`。

### 6.1 裁判自查

1. **每一条进入排名的 bug,裁判必须亲自打开 `file:line` 核对。**
2. **文档写得详细不等于 bug 真实。**
3. **无法判定的**标记 `UNVERIFIED`,不计入有效分,并公开列出。
4. **裁判的复核脚本必须有对照组,且贴对照组输出**(§4.7)。
5. **裁判报告里的每一处行号引用自己再核一遍**,不复述选手的转述。
6. 裁判结果如有错判,选手可申辩(§6.7),裁判复核后修正并**公开记录修正过程**。

### 6.2 计分公式(满分 100)

#### 发掘分 70

```
单条得分 = 严重度基数(S) × 证据系数(E)
严重度基数:S1=10, S2=6, S3=3, S4=1
证据系数:  E3b=1.0, E3a=1.0, E2=0.8, E1=0.5, E0=0
同一条缺陷被两人发现:各人照常计分(不设唯一归属)
落在 §3.4 已知清单里的:0 分(双方都是)
E1 条目未答前置可达性三问的:严重度按 S4 计(基数降,证据系数不变)
发掘分 = Σ(有效条目得分),上限 70
```

量级参考:

| 典型产出 | 算式 | 发掘分 |
|---|---|---|
| 3 条 S2/E2 | 6×0.8 ×3 | 14.4 |
| 5 条 S2/E3 | 6×1.0 ×5 | 30 |
| 1×S1/E3 + 5×S2/E3 + 2×S3/E2 | 10 + 30 + 4.8 | 44.8 |
| 2×S1/E3 + 6×S2/E3 | 20 + 36 | 56 |

额外扣分:
- 正式报告区(不含自我否定清单)`E0` 占比 > 50% → 记「低证据密度」,**评审分 -5**。
- 严重度虚报(§4.3)→ **-3/条**。
- 违规(§8)→ 见扣分表。

#### 评审分 30

| 项 | 分值 | 规则 |
|---|---|---|
| 裁决正确率 | **15** | 见下方对照表,封顶 15 |
| 抽验质量 | **7** | 抽验条目中「你的复验结论与事实一致」的比例 × 7;未做抽验直接给 0 |
| 主动新发现 | **5** | 按 `S×0.5` 计:S1=5, S2=3, S3=1.5, S4=0.5(以裁判复核为准),封顶 5 |
| 交叉洞察 | **3** | 按 `S×0.3` 计:S1=3, S2=1.8, S3=0.9, S4=0.3。**不设上限**,但与「主动新发现」互斥(§5.4) |
| 行号核实 | 扣分项 | 裁判抽查 3 条你的引用,核错一处 **-2** |

#### 裁决「一致 / 不一致」的判定表(本场事前钉死,修上届缺陷 3)

设裁判终裁为 `V`,你的裁决为 `J`:

| 你的裁决 | 裁判终裁 | 判 |
|---|---|---|
| `CONFIRMED` | `CONFIRMED` | 一致 |
| `PARTIAL`(修正后的严重度与终裁同档) | `PARTIAL` | 一致 |
| `REJECTED` | `REJECTED` | 一致 |
| `KNOWN` / `DUPLICATE` | 同源 | 一致 |
| `REJECTED` | `PARTIAL` | **一致**,但仅当你的原文把否决范围限定为「作者当前版本的主张不成立」**且**给出了可成立的改写版本;否则算不一致 |
| 任何其它组合 | | 不一致 |
| `NOT-ENOUGH-EVIDENCE` | `CONFIRMED` | 不一致,且**额外 -1**(放过真缺陷) |
| `REJECTED` | `CONFIRMED` | 不一致,且**额外 -2**(误杀真 bug) |

> **上届的两条口径先例,本场沿用**:
> ① **评审比裁判终裁更严,不算「不一致 -2」**——规则要扣的是「放过真缺陷」与「误杀真 bug」两个方向,比事实更严不在这两个方向里(前提是你把否决范围写清楚了)。
> ② **同一处代码被两方独立发现同一洞察,各自照常计分**,裁判在裁定书里点名重叠而不扣分。
> ③ **虚报 -3 不触发的常见情形**:你的评审已经证伪了作者 → 说明「环节二已被证伪」不成立。

2. 评审误判少者胜

### 6.7 申辩条款

裁定书如有错判,可申辩,裁判复核后会修正并**公开记录修正过程**。有效申辩需包含:① **具体的 `file:line`**;② **可复现的证据**(命令 + 真实输出,或精确的调用链推演)。只提交「我不同意」不构成申辩,裁判会退回并说明理由。

|---|---|---|

## 8. 给选手的临门一脚

这个仓库 156 万行,其中 100 万是一手代码。**已经被扫过两轮**:

- `docs/bugs/` 的 22 条已知缺陷(2026-10-05 两轮并行审计)——对账后**只剩 7 条**仍需动手(§3.4 A 组)。
- 上一届 `bug-hunt-game-10-16` 的四家选手 —— 24 条声明,去重后 28 个独立缺陷,**其中 22 条已在本场基准提交前修完**(§3.4 B 组)。

**这两片都已经被扫过了,你的价值在它们没扫到的地方。而且这次局面变了:上一届的修复刚落地不到一天,新代码就是新的排查面。**

**真正值钱的 bug 在缝隙里**:

- **跨模块契约不一致** — `packages/zai`(Express+SSE)与 `packages/zn-agent-core`(vendor opencc + compat 垫片)之间的假设。`src/compat/` 这层垫片的每个函数都是一个「两套实现语义不一致」的机会。
- **模块级单例的生命周期** — 三个单例 registry、instanceStore、session registry、weixin account locks、PTY 会话表。**上一届的核心发现是「状态分散在多个注册表,移除路径只清了其中几个」,本仓库大概率还有同构问题。**
- **上一届刚落地的 16 条修复本身** — 修复引入的新缺陷、修复只堵了一半的路径。**这一片是全新的,没人扫过。**(`cc-r2` 的 boot 期无条件自动写、`oc-004` 的并发清理竞态都出自修复方案的边缘。)
- **异步竞态与状态残留** — Express 4 不转发 async rejection、SSE 订阅注册晚于 `await`、`req.on('close')` 的语义。
- **fork 特有改造** — `src/compat/sandboxManager.ts`、`src/compat/permissions.ts`、`src/compat/dangling-shims/`、`src/compat/subprocess/`。
- **特性开关与部署形态** — `--lan` 模式打破「只监听 localhost」这个安全前提(§3.4 A 组两条安全缺陷就靠它)、微信通道只跑在受管子实例、`ZAI_DATA_DIR` 的静态 import vs 函数重读。

**不要为了赢而堆 E0。** 一条被裁判亲自核实为真的 S2,比二十条看起来很专业的猜测值钱得多——而猜错还要倒扣。

**也不要为了显得严谨而堆 E1。** typecheck 基线是干净的(exit 0),所以 typecheck 红的信号很强;但**它抓不到运行时行为问题**,而后者才是这个仓库的主要缺陷面。**E1 是起点,不是终点**——但 E1 必须先答完 §4.2.1 的三问。
