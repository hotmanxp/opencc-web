# P3.1 Spec — ReplRuntime 直接接 vendor query()

**日期**: 2026-08-30
**作者**: opencc-web P3 接续
**状态**: DRAFT(待审批 — 修正稿)
**目的**: 让 zai ReplRuntime 真正调通 vendor `query()`,产出 turnEnd,让 zai web UI 看到 assistant 响应。

## 0. 关键澄清(2026-08-30)

**P3.1 不是"zai 接入 OpenccRuntime"**。zai 早就接了:

- `packages/zai/src/server/services/agentRuntime.ts:86` `let runtime: OpenccRuntime | null = null` — 单例已存在
- `initAgentRuntime()`(L578+)分支:
  - `'repl'` → `runtime = new ReplRuntime() as unknown as OpenccRuntime`(P3 stub)
  - `'default'` → `runtime = await createOpenccRuntime({...})`(L769,真 vendor)
  - `'inproc'` → `createPrintRuntime`(L729,真 vendor)
  - `'spawn'` → `SessionHostRuntimeAdapter`(L599,真 vendor)

**P3 的设计目标**(由用户 2026-08-30 澄清):zai 的 `ReplRuntime` 是把 opencc CLI REPL 的 UI 行为用 zai web UI 重现,**直接接 vendor `query()` 方法**(在 `packages/zn-agent-core/src/opencc-src/query.ts:501`),不走 OpenccRuntime 抽象。cast 成 OpenccRuntime 是为了 zai 单例类型统一。

**P3.1 真目标**:让 `createReplSession.runTurn → vendor query()` 真正跑通,产出 turnEnd,UI 不再卡"对话中"。

## 1. 背景

P3 (2026-08-30 inproc-repl-extract-p3-stub-completion) 把 zai 默认 runtime
从 `'default'`/`'inproc'` 切到 `'repl'`(stub),意图是 zai web UI 复刻 opencc
CLI REPL 行为。

**当前问题**:
- `agentRuntime.repl.ts:74` `ReplRuntime.query()` 调 `session.submit(input.prompt)`(stub,只 emit `runtime.started` + 不 emit `runtime.done`)
- `createReplSession.runTurn`(createReplSession.ts:537) 真调 vendor `query()`,但 hang 在某种等待上,永不 emit `turnEnd`
- UI 永远卡"对话中",无 assistant 响应

066fc22d defensive `toolPermissionContext` fix 让 vendor `getTools()` 不崩,
但 vendor query() 本身没真正工作。

`docs/superpowers/verification/2026-08-30-fresh-smoke-v2/report.md` 详细记录。

## 3. 关键设计决策(待 user 审批)

### 3.1 vendor query() 的依赖(deps)谁负责注入?

- vendor `query()` 签名(L501-519):`export async function* query(params: QueryParams)`
- `params.deps ?? productionDeps()` — 没传 deps 就用 vendor 默认
- vendor 默认 `productionDeps()` 创建真 API client(Anthropic SDK),需 `ANTHROPIC_API_KEY` env
- zai ReplRuntime 路径下,createReplSession.runTurn 没传 deps,走 vendor 默认

**决策**:
- 选项 A(推荐):zai server 启动时设 `ANTHROPIC_API_KEY`(从 `~/.zai.json` 第一
  个 provider profile 读)到 env,让 vendor 默认路径自然跑通
- 选项 B:createReplSession.runTurn 显式构造 deps(zai `modelCaller.ts` 已有),
  走 zai provider router
- 选项 C:沿用 vendor 默认(需 user 自己设 env)

**推荐 A**,最小改动,但要求 `~/.zai.json` 有 provider profile。

### 3.2 vendor query() hang 在哪里?

需要调查的 hang 候选点:
1. `productionDeps()` 创建 API client 时(如 token 校验)
2. `queryLoop` 第一轮 `model.generate()`(真 API 调用)
3. `ToolUseContext.getAppState()`(066fc22d fix 了)
4. `runWithSdkContext` / `runWithSessionId` ALS 切换
5. `setupSkillsChange` chokidar(已修)
6. MCP server 连接等待

P3.1-T1 调查后再决定 fix 路径。

### 3.3 测试基础设施

- P3 单测 mock `query.js`(`createReplSession.query.test.ts`)
- e2e 需要真实 API key + 网络
- **决策**: P3.1 e2e 用 zai 当前 `~/.zai.json` 第一 provider profile + API key。
  跑通 = vendor query 真正能调 LLM。如果连不通,标记 fail 并给出修复方向,
