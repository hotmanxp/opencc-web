## lan-agent 0.9.1 — 修 `updatedAt` 浮点导致会话列表整页报错

承接 9-13 的 0.9.0（原生 Agent 会话列表 + 详情）。超哥真机装完直接报错：

```
Unexpected JSON token at offset 175: Unexpected symbol ':' in numeric literal
at path: $.sessions[0].updatedAt
input: ....At":1789315591018,"updatedAt":1789274126878.9248,"title":"帮我.....
```

**根因**：`GET /api/agent/sessions` 的 `updatedAt` 来自 Node `fs.Stats.mtimeMs`
（`zn-agent-core/src/compat/runtime/legacyTranscriptStore.ts:262` `updatedAt = s.mtimeMs`），
是**带小数的 double**。我在 `AgentSessionMeta` 里声明成了 `Long` → 解码抛错 → 列表页空白。

**实测确认不是偶发**：本机 4 个在跑实例（9201/9933/9988/9955）拉下来统计，9933 那个
**115/115 条会话的 `updatedAt` 全部是 float**（`createdAt` 全是 int，走 `Date.now()`）。
字段全集只有 8 个：`sessionId / cwd / model / permissionCode / providerId / createdAt / title / updatedAt`。

**修法**（`lan-agent`）：
- `AgentModels.kt` 新增 `EpochMsSerializer` / `EpochMsNullableSerializer`
  —— 容忍整数 / 浮点 / 数字字符串 / ISO 字符串，取整误差 < 1ms。
  逐个挂到 `AgentSessionMeta.createdAt|updatedAt`、`TranscriptMeta.createdAt|updatedAt`、
  `SessionCwd.updatedAt`、`V2Task.updatedAt`。
- `toEpochMs()` 补浮点分支（原来只 `toLongOrNull()` + ISO parse，浮点会 null 掉）；
  `JsonObject.long(key)` 改为走 `toEpochMs()`。
- **新增 JVM 单测基建**（项目原来 `app/src/` 下只有 `main`）：`testImplementation(kotlin("test"))`
  + `app/src/test/java/.../data/AgentModelsTest.kt`，5 条用例覆盖浮点 mtime / 双形态 timestamp /
  stat 失败回 0 / 未知字段容忍 / tool_result 三形态。`./gradlew :app:testDebugUnitTest` → 5/5 绿。
- 用真实响应（`curl :9933/api/agent/sessions` → 115 条）跑了一次临时解码 smoke 闭环验证
  （decoded 115、updatedAt<=0 的 0 条），验证完删掉临时测试与样本。
- 版本 0.9.0/33 → **0.9.1/34**；`AGENTS.md` §14 与 `README.md` 已同步这条坑。

**要点（跨项目通用）**：zai 没有 OpenAPI / JSON Schema，wire 类型全靠实测倒推。
任何数值型字段都可能出现浮点（连 `2.0` 这种整数浮点也会让 Kotlin `Long` 解码器炸），
时间戳一律走容错序列化器，别按「服务端应该给整数」赌。

  JPEG 压成黑底。
- `AgentApi.sendPrompt` 支持 `contentBlocks`。**关键契约**：文本只能走顶层
  `prompt`，服务端自己拼（`agent.ts:1201-1204`），客户端再加 text block 会让
  用户看到自己的话重复两遍 → 抽成纯函数 `promptRequestBody()` 供单测钉住。
- `AgentSessionScreen.kt` — 顶栏瘦身（去掉 4 个 action，刷新/在网页打开/全部元信息
  收进**副标题点开的 BottomSheet**，状态标签只在非空闲显示）；空态改成
  大图标 + 大字 + 副文案；接线语音、图片、粘贴。
- 新增 4 条单测 `AgentApiBodyTest`（9/9 绿），版本 0.9.1/34 → **0.9.2/36**。

**踩到的小坑**：`@Stable` 的 import 是 `androidx.compose.runtime.Stable`（`stable` 是包名）；

## zai — 修 BashTool cwd wrap 吞掉返回值的崩(P0)

用户报 `Cannot read properties of undefined (reading 'data')`。根因在 commit `a14eab72`
引入的 `compat/tools/opencc/bashCwdWrap.ts`:`wrapBashToolWithCwdSync` 的 `call` 只
`await originalCall(...)` 就返回,**没有把 vendor ToolResult 传出来**。vendor 调用方
`opencc-src/services/tools/toolExecution.ts:1481` 是 `const result = await tool.call(...)`
紧跟 `:1504` 读 `result.data` → `result` 为 undefined → 每次 Bash 调用都炸。

定位手法(bundle 反查):dist/opencc-core.mjs 里搜 `sessionProjectDir:null,cwd` 能唯一命中
wrap 构造 SdkContext 的那段(minified 后函数名变 `_5n`),直接看到 `await Tk(a,...)` 后没有 return;
同时确认 `wZn=_5n(lr)` 被喂进 `getAllBaseTools()`(vendor tools.ts),而 runtime 工具池走
`createOpenccRuntime-impl.ts:153 assembleToolPool` ← `getAllBaseTools()`,所以 wrap 确实在
live 路径上;`compat/tools/opencc/builtin.ts` 的 `getOpenccBuiltinTools()` 全仓无人调用(dead)。

修复(`packages/zn-agent-core/src/compat/tools/opencc/bashCwdWrap.ts`):
- `const result = await runWithSdkContext(ctx, () => originalCall(...))` → 写回 CwdStore 后 `return result`;
  顺手把 `async () => { await ... }` 改成返回 promise 的箭头,throws 语义不变。
- 新增 `get checkPermissions()` 转发到 raw tool:wrap 在 bundle module-init 就跑,比 compat
  `forceAllowCheckPermissions()`(Object.defineProperty 打在 raw 上)早,spread 拷贝会把 override 冻住。
- 测试补 3 个用例(返回值 ×2 + checkPermissions 转发),11/11 绿;做了红检(去掉 return → 新用例失败)确认能抓 bug。
- `pnpm run build:core` 重建,dist 里已确认 `return l`;tsc --noEmit 干净;compat 106 测试全绿。

**教训**:透传型 wrapper 必须显式 `return`+rethow;8 个单测只断言副作用(CwdStore)不校验返回值契约
= 盲区,新增/改 wrapper 时先写一条"返回原值/原样抛错"的用例。

## zai — cwd 不保持的真因:vendor `resetCwdIfOutsideProject` 回归(P1)

接上一条(返回值崩)修完后用户复测:`cd /tmp && pwd` 给 `/tmp`,下一轮 `pwd` 又回项目根,
tool 输出带 `Shell cwd was reset to ...`。

**根因不是 wrap,是 vendor**:`opencc-src/tools/BashTool/utils.ts` 的
`resetCwdIfOutsideProject()`(BashTool.tsx:819-824 调用)在每次前台 Bash 调用后,
若 cwd 漂出 `originalCwd + additionalWorkingDirectories`,就 `setCwd(originalCwd)` 拉回。
它在 `BashTool.call` 内部执行 → 早于 wrap 读 `ctx.cwd` → 漂出的 cwd 永远进不了 CwdStore。

**这是回归**:zai 2026-07-19 设计就要求该函数 `return false`
(`docs/superpowers/specs/2026-07-19-zai-bash-cwd-tracking-design.md` §1.3/§6.3,
stub 在旧 `zai-agent-core/src/tools/BashTool/utils.ts`,commit `7d32eacb`),
opencc 0.20.0 un-stripped 重拷(`98ee7e5a`)把上游真实实现带回来了。

**修法**:在 `opencc-src/tools/BashTool/utils.ts` 重打 stub(参数保留、返回 false,
删掉随之失效的 5 个 import);新增金丝雀
`test/unit/compat/vendor/bashCwdResetStub.test.ts`(cwd 漂出 allowed dirs 时断言
返回 false + 不调 setCwd + ctx.cwd 不变),上游实现一回来就红(已红检)。
验证:compat 107 绿、`tsc` 干净、`build:core` 后 bundle 里
`tengu_bash_tool_reset_to_original_dir` 引用 0、`function Cbe(e){return!1}` 仍在两处被调。

**方法论沉淀(两次都靠它)**:vendor 行为不对时,先 `git log -S <符号>` 查该符号在
旧 zai-agent-core 树里的历史 —— opencc 0.20.0 重拷贝会静默覆盖 zai 旧 patch,
旧设计文档(docs/superpowers/specs/2026-07-19-*)里的"stub 表"就是契约清单。

## zai — 修 mermaid `rect` 色块不铺底色(beautiful-mermaid 上游缺陷)

用户截图:sequenceDiagram 里 `rect rgb(245,245,245)` 渲染成左上角一行
`rect [rgb(245,245,245)]` 文字,块内没有底色。

**根因在上游库**:beautiful-mermaid@1.1.3 的 `src/sequence/parser.ts` 把 `rect`
收进了 block 白名单(`loop|alt|opt|par|critical|break|rect`),但
`src/sequence/renderer.ts` 的 renderBlock 走通用分支 → 块底 rect `fill="none"`,
label(颜色字面量)被当作 `${type} [${label}]` 画成标题 tab。npm 上 1.1.3 已是最新,
无上游修复。

**修法(不 patch 依赖,在自己层后处理)**:`mermaidRenderer.ts` 新增
`applyRectBands(svg, theme)`,在 sanitize 之后用正则按
`<g class="block" data-type="rect" data-label="...">…</g>` 整组改写:
1. 块底 rect 的 `fill="none"` → label 解析出的颜色(严格校验 hex/rgb[a]/字母色名,
   非颜色字面量一律不写入属性,避免注入面);
2. 删掉 tab rect(`fill="var(--_group-hdr)"`)与标题 `<text>`(rect 组内唯一的文本);
3. 消费掉 `data-label`。
透明度:深色主题 `fill-opacity=0.18`(LLM 常给 `rgb(245,245,245)` 这类浅色,深色
画布上原样铺满会把文字压死);`MermaidTheme` 新增可选 `mode`,由 MermaidBlock 从
`<html data-theme>` 读取,缺省按 bg 亮度推断。
对比度下限:颜色与画布底色亮度差 < 0.05 时朝文字色混 12%(浅色画布 + 245 灰 → 217,
否则"还是看不见底色")。

**验证**:`mermaidRenderer.test.ts` +9 用例(单测 applyRectBands ×6 + e2e ×2 +

## zai — mermaid 宽图撑破消息列(尺寸/自适应)+ elkjs 体积真相

用户问"宽高怎么确定的、为什么超出宽度"。

**尺寸链路**:beautiful-mermaid 在 layout 阶段按文本度量算出绝对画布尺寸,根标签是
`<svg width="1370" height="628" viewBox="0 0 1370 628" style="--bg:…">`——没有任何
max-width;MermaidBlock 原来只有 `overflow-auto`,挡不住宽图把消息列
(`.ant-space-item{min-width:auto}`)一路顶开。

**修法**:
- `mermaidRenderer.ts` 新增 `makeSvgResponsive(svg)`:给根 svg 补
  `max-width:100%;height:auto;min-width:round(W*SVG_MIN_SCALE)px`
  (`SVG_MIN_SCALE=0.75`)。min-width 是缩放下限:纯 max-width 会把 1370px 图压进
  410px 面板(比例 30%,11px 正文变 3px 完全没法看);到下限后交给外层横向滚动。
- `MermaidBlock.tsx`:外层 `w-full min-w-0 max-w-full` + `[&_svg]:block
  [&_svg]:max-w-full [&_svg]:h-auto`(Tailwind 任意变体)。

**实测**(ego-browser,8120 dev):自然 1370×628、容器 1051 → 渲染 1027(75%)、
字号 8.2px;把容器压到 400 → svg 停在 1027、块内可横向滚动、页面零溢出;小图
440 不被放大。测试 38/38 绿(mermaidRenderer 27 + MermaidBlock 11),tsc 干净。

**副产品/纠正**:`mermaid-beautiful` chunk 实测 **1.59MB / gzip 490KB**,不是仓库注释
里写的 "~30KB" —— beautiful-mermaid 的 dependencies 里有 `elkjs@^0.11`(dist/index.js
335KB + elkjs ~1.2MB)。也就是说移除官方 mermaid 库时,elkjs 被 beautiful-mermaid
自己带回来了。已改 `vite.config.ts` 与 `mermaidRenderer.ts` 的注释。真要瘦身得换
renderer 或按需加载 layout。

**流程注意**:9201 实例走 dist/web 构建产物,前端改动后要 `pnpm build:web` 才生效
(已重建)。
